# Tablet native content v6/v7

Existing pairing, ECDSA request signatures, preview encryption and v1-v5 messages remain compatible. v6 is read-only: both sending capability flags MUST be false. Existing 48h createdAt window and global per-device seq apply. No account identifiers or plaintext content enter logs.

POST /api/v1/android/messages adds v=6, contentEnvelope and nativeAssets (at most 8); legacy assets is empty. Preview stays within 600 UTF-8 bytes. Native content is at most 1 MiB plaintext. Envelope alg=A256GCM, kid=phase2-content, AAD=`AWR1|A2I_CONTENT|6|messageId|deviceId|seq|createdAt|wechatUserId`. UUIDs lowercase. JSON encrypted with existing kA2I.

Decrypted content v=1: {v, conversationId, conversationName, senderId, senderName, isOutgoing?, kind, text, rawXML?, attachments: [{assetId, name, sha256?, recordItemIndex?}], records?: [{senderName, kind, text, rawXML?}]}. kind is text/image/audio/video/file/sticker/reference/record/link/unsupported. conversationId is the original stable WeChat identifier, scoped by pair and profile in clients. rawXML is retained as original data, never interpreted as HTML. Records preserve all text/XML available in the source, without claiming absent embedded files exist. recordItemIndex is a zero-based index into records and must be in range; original and playback attachments use the same index. Unindexed attachments remain at message level.

The encrypted content may also include isOutgoing:boolean (default false), preserving the original message direction.

图片 attachment 可在加密内容内添加三个可选字段: `sourceRepresentation:"native_db_decoded"`, `sourceByteLength:<XML 源声明长度>`, `originalBytesVerified:false`. 它们用于官方微信下载后转码的完整 JPEG 缓存, 文件名为 `wechat-decoded.jpg`, `sha256` 是实际上传 JPEG 的 SHA-256. 采集必须匹配精确消息/会话和最高 quality row, 验证 native 完成计数等于实际文件长度, MD5(path-size) key, 稳定读取及 JPEG 签名. `ImgInfo2.origImgMD5` 的 path-size key 不是内容 MD5, XML 源长度也不要求等于转码 JPEG 长度. XML 内容 MD5 和对应资源长度完全匹配的原件分支继续保留.

nativeAssets: [{id, kind, mimeType, byteLength, role, derivedFrom?}]. kind=image/sticker/audio/video/file; role=original/playback. byteLength is an integer 1..8388608. Metadata is immutable and declared before upload. Playback representations use a separate id and derivedFrom referring to an original asset. Filenames live only in the encrypted content. Unknown size or unavailable bytes must not be invented. Collector waits for a measurable original when no reliable size is recorded. Files larger than this bound are reported explicitly, never truncated.

上述官方转码 JPEG 在 v7 `nativeAssets` 中仍使用 `role=original`, 表示原采集附件, 不证明与 XML 源文件逐字节一致; `byteLength` 始终声明实际上传文件长度. 三个表示字段仅进入加密内容, 不修改 Server API, AAD 或公开 metadata, 旧 iPhone 可忽略未知字段. 已封装消息和附件保持不可变.

POST /api/v1/android/messages/:messageId/assets/:assetId uses existing signed Android auth and body {envelope}. Envelope kid=phase2-asset; AAD=`AWR1|A2I_ASSET|6|messageId|assetId|deviceId|seq|createdAt|wechatUserId|kind|mimeType|byteLength|role|derivedFromOrEmpty`. Ciphertext length is byteLength+16. Retry byte-identical envelope with a fresh signature nonce. Ownership and metadata checked against stored v6 message. First successful durable write returns 201, identical retry 200, different envelope 409. Original message acknowledgement does not acknowledge attachment upload.

Authenticated iOS message list adds optional hasNativeContent=true and nativeAssets. Full content is NOT in list pages. GET /api/v1/ios/messages/:messageId/content returns {contentEnvelope}, with existing iOS auth and pair isolation. GET /api/v1/ios/assets/:assetId returns {id, kind, mimeType, byteLength, role, derivedFrom?, envelope} for v6. Pending known asset returns 409 code ASSET_PENDING, expired returns 410 code ASSET_EXPIRED, unknown/wrong pair returns 404. Legacy asset behavior remains unchanged. iOS must retry pending assets on user action, reconnect or a bounded foreground refresh, without relying on arrival of a new message seq.

Storage uses existing MySQL, new native content/asset tables and schema migration 8. Asset envelope serialized ciphertext <=12 MiB, transactionally published with no overwrite. Validate max_allowed_packet >=16 MiB. TTL is 7 days from message received_at; identical retries do not extend TTL. Pair quota is 256 MiB of declared plaintext bytes, with serialized reservation under the existing device row lock; expired rows cleaned before reservation. This deliberately bounded path avoids a new service or filesystem storage mount. Upgrade to chunked object storage when larger files or measured database load requires it.

The collector durably stores UUID/seq/sealed request in a private SQLite outbox before network calls; retries never reseal. No source DB writes, checkpoints, injection, forwarding or transcription. Read source through a private read-only mount namespace and SQLCipher read transaction. Source identity includes account fingerprint and msgId/msgSvrId, not row position alone. Never put pairing keys in command arguments, logs, repository or chat.

## v7 and tablet replies

v6 remains read-only. New collector messages use v7, and the `A2I_CONTENT` / `A2I_ASSET` AAD version is 7. The message list adds `nativeVersion:6|7`; older responses default to 6. `conversationSendCapable` remains false for native messages. `replyCapable` is true only for new private-contact messages with one source contact/alias, an installed reply key, and an available official-UI adapter. Group messages remain read-only. Cached and uploaded v6/v7 requests are immutable, including capabilities; installing the adapter does not rewrite old messages or fabricate a new message timestamp.

Encrypted v7 content adds `accountFingerprint` and `replyIdentity` from the read-only source. The contact candidate is `replyIdentity:{username,contact:{username,alias}}`; group, missing or ambiguous contact records omit `contact`. A contact candidate is not UI recipient proof. Every send re-reads the source identity and requires the official WeChat profile page's exact WeChat ID to match the source alias before returning to the same chat/composer.

The existing `replies` table stores tablet commands without a schema migration. New commands retain `targetMessageId`, pair/device/profile authorization, existing signed polling and signed ACKs. They are delivered exclusively through `GET /api/v1/android/replies/tablet`; legacy Android polling excludes them. Tablet polling may return the same `DELIVERED_TO_ANDROID` command until its terminal ACK. The local private journal deduplicates immutable command IDs and records `COMMITTING` before starting the UI adapter. Recovery from that state yields `SEND_UNCONFIRMED`, never an automatic second click. Tablet terminal ACKs are idempotent and cannot change a previous terminal outcome.

- Reply command v5 uses `kid=phase1-reply`, the existing `kI2A`, and AAD `AWR1|I2A|5|TABLET_SEND|pairId|replyId|deviceId|targetMessageId|createdAt|0`. Plaintext is `{body,conversationId,accountFingerprint}`. The target must be a reply-capable v7 message owned by the same pair/device. Up to 1000 Unicode scalars are accepted. Tablet command ciphertext is at most 8192 bytes.
- Reply control v6 uses `kid=phase2-reply-bootstrap`, AAD `AWR1|I2A|6|REPLY_KEY_BOOTSTRAP|pairId|replyId|deviceId|targetMessageId|createdAt|0`, and a separate 32-byte key derived by HKDF-SHA256 from `kA2I`, salt `UTF8(pairId)`, info `UTF8(AWR1|TABLET_REPLY_KEY_BOOTSTRAP|deviceId)`. Plaintext is `{v:1,pairId,deviceId,replyKey:<existing kI2A base64url>}`. The target may be an existing read-only v6/v7 message. A matching existing key is idempotent; a different key is rejected. The control only atomically adds `kI2A` to the existing private config, then ACKs `REPLY_KEY_INSTALLED`; it cannot enter UI sending. Pair, device, signing key, source cursor and message outbox are preserved. `kA2I` is never reused as the reply key.

`GET /api/v1/ios/status` advertises `tabletRepliesAvailable:true`. iOS defaults missing capability to false and does not bootstrap against older servers. The immutable bootstrap command is persisted separately from outgoing messages; failed optional initialization does not fail normal inbox refresh. If its submit result was uncertain, iOS first queries the command status. Only an explicit 404 plus expiration permits a new control ID; accepted commands are never blindly replaced.

The reply consumer is an independent process with its own SQLite connection and lock, so attachment uploads cannot starve polling. It checks current relay policy and the two-minute command age after source reading, and the native adapter checks expiration again immediately before clicking. The collector reloads only a compatible atomic config update; pair/device/signing/message-key changes or replacing a known reply key fail closed.

The internal source reader returns `sourceMaxId`, computed with `MAX(msgId)` in the same read-only transaction as the selected messages. Reply reads omit media bytes. Immediately before committing the click, the helper writes a private source-check request containing replyId, SHA-256 of the original command UTF-8 bytes, and a fresh UUID nonce. The guest rechecks the source account/message/recipient and atomically grants the current watermark with an expiration no later than the command expiry or two seconds from that check. The helper binds all fields, refreshes the same composer and send button, and enforces expiration again after journal commit. Denied grants cannot click. Older readers/adapters without this evidence fail closed; update the reader, consumer, guest adapter and helper together.

`SENT_TO_WECHAT` requires the official UI to accept the click plus one source message whose ID is strictly above the pre-click grant watermark, with exact account, talker, body, outgoing direction, creation time near the reported click and a nonzero server message ID. Previously existing identical text cannot confirm a send. UI clearing alone is insufficient. Missing or ambiguous source evidence yields `SEND_UNCONFIRMED`; this does not prove recipient receipt. Source checks reduce account-switch races but do not provide an atomic official-UI self-account credential. The official UI selectors and actual device behavior are not validated by synthetic protocol checks.
